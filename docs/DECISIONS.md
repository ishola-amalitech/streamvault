## Implemented acquisition and preparation

### D01 · Account for each input and reuse successful responses

The input contract is a single `tmdb_id` column. The parser keeps the first occurrence of a valid positive numeric ID and records blanks, invalid values and repeated entries with source line and reason. The client requests movie details with credits appended, using one shared HTTP session. Configuration supplies eight concurrent workers, four request starts per second, 10-second total and 3.05-second connect timeouts, and up to three retries after the first attempt for network errors, HTTP 429 and HTTP 5xx. Retryable HTTP responses use a valid `Retry-After` value when present. Otherwise the initial delay is 0.5 seconds and doubles for each retry.

Cache the successful JSON responses by ID in JSONL, stamp them in UTC, and replace the file atomically. The backfill timestamp indicates when an existing entry was stamped. Reuse cached IDs and retry uncached IDs on subsequent runs. The removal log records 404s and empty responses alongside malformed or duplicate inputs. The CLI prints terminal request failures with IDs and keeps the latest unresolved outcome by ID in `out/movies.acquisition.json`. A successful cache entry supersedes any older missing or failed result.

The command can replay a saved list without a token when every uncached ID already has a recorded outcome. It stops if an uncached ID has no outcome, since that film might change either shortlist. With a token, the command retries uncached IDs. A replay uses the last recorded evidence until Adjoa retries. Older snapshots can still use an acquisition record saved beside the raw cache. [Pipeline](../src/streamvault/main.py)

The pipeline, all four notebooks, and the benchmark use the same cache reader and candidate matcher. The cache reader returns IDs in the same format as the CSV parser, so a legacy string such as `00123` matches ID `123`. Each entry point reports repeated IDs on the current list and stops before using those records. Older films stay available in the cache for future runs. Profiling the full cache could mix older titles into today's statistics and overstate the evidence behind the recommendation. After downloading, it checks that every requested ID has exactly one outcome before writing new responses to the cache. Notebook 01 uses the same ID parser to account for every CSV row and reads logged lookup misses by ID. The source parser treats IDs such as `00123` and `123` as one numeric ID for both fetching and analysis, and keeps the original text for the audit. A missing source file stops the download command so a wrong path cannot look like an empty list. Notebook 04 calls the parser without writing a removal log and scopes the cache to the current list. For an uncached ID, it uses the acquisition record first and falls back to an older lookup miss in the removal log. Matching by ID preserves the outcome when a row moves. These records describe the last known attempt. Notebook 04 stops if a candidate is missing from the cache and has no logged reason, because an unexplained gap could affect the shortlist. Refreshing the whole cache each run would provide fresher metrics at the cost of more API traffic, slower meetings, and comparisons against different snapshots. ### D02 · Keep film, relationship, and credit grains distinct

Assign the stable keys when normalizing. Keep one movie row per `movie_id`, with an optional `collection_id`. The reference tables contain one row per entity, and links for multiply occurring attributes live in bridge or credit tables. Cast and crew retain popularity at the credit level because a person's value can differ between cached movie responses.

| Grain | Tables and keys |
| --- | --- |
| Film | `movies`, keyed by `movie_id` |
| Reference entity | `genres.genre_id`, `companies.company_id`, `countries.country_code`, `languages.language_code`, `collections.collection_id`, `people.person_id` |
| Film–entity link | `movie_genres`, `movie_companies`, `movie_origin_countries`, `movie_production_countries`, `movie_spoken_languages`, each keyed by `movie_id` plus the entity key |
| Credit | `cast_credits` and `crew_credits`, keyed by `credit_id`, with film and person references |

The pipeline normalizes only resolved films from the current list. It stops if its structural checks for film IDs, genre and credit links, or the collection join fail. The tables stay in memory. The pipeline saves film issues in `out/movies.quality.csv`. Notebook 04 writes its own copy beside the cache. [Pipeline](../src/streamvault/main.py) · [Pipeline tests](../tests/test_main.py)

Notebook 01 runs 41 staged report checks on the current nonempty input. These include three for loading current candidates, 29 for normalized tables, six for the illustrative genre joins and three for source coverage. It also runs a cross-table join audit across seven bridges or credit tables and the optional collection and company-country references. Required joins use left joins and declared cardinality, with indicators to expose unresolved IDs. The current 320 genre links survive both reference joins. Source coverage checks one outcome per input row using current parser results, cached movies, and logged lookup misses. Normalization and merge cardinality can raise before a report.

The raw loader checks JSON, object shape and positive numeric IDs. The normalizer rejects malformed relationship shapes or dates, duplicate movie/relationship/credit keys and conflicting reference attributes. Notebook 02 checks raw lines across the whole cache for identical entries and labels that audit separately. Its normalized tables and title-and-year screen use the current candidate list. A rough title-and-year match remains a manual-review candidate. A flat table could be quick to inspect, but aggregating money on exploded genre or credit rows would overcount films. Aggregate to movie grain before attaching relationship measures. ### D03 · Treat validity, missingness and plausible extremes according to their effect

Normalize blank text to missing and parse release dates. Preserve optional text or reference-label gaps. Keep nonnegative numeric fields and a 0–10 vote rating as validity expectations. Notebook 02 reports numeric ranges and release-date coverage after normalization. Notebook 04 applies eligibility rules to each measure. Calculations that use both budget and gross require usable positive amounts for both.

The pipeline and Notebook 04 report missing release dates or statuses, missing or invalid rating inputs on dated, released films, and missing, zero, or invalid budget and gross. Films with no date or status stay in the audit and out of both comparison windows. Films without a rating from 0 to 10 or a finite, nonnegative whole vote count stay unscored. One unscored observed installment makes its bundle ineligible in that window. A film whose budget or gross is unusable can still receive an audience score. Financial calculations use the positive amounts they need and show how many films contributed. Both entry points stop on repeated in-scope cache IDs, missing or unreadable cache timestamps, broken joins, or implausible years on dated releases. The allowed year range runs from 1880 to the newest in-scope cache timestamp year. The CLI can backfill missing cache timestamps before the analysis. [Recommendation inputs](../src/streamvault/recommendation_inputs.py)

The pipeline and Notebooks 03 and 04 now share `financial_inputs()`. It produces one usable dollar amount and an issue reason per field. A zero gets its own reason because it gives us no usable amount. Negative values, infinity, and values that cannot be read as numbers are invalid. Checking the two amounts independently keeps a known gross in gross-only summaries even when budget is unusable. Paired measures use only films with both values. Replacing gaps with zero would make comparisons depend on how much data is missing. The cached values stay as received. Log amounts are calculated inside the exploratory models that use them. [Financial checks](../src/streamvault/movie_quality.py)

The standalone candidate reports show the source gross as `raw_gross` and the checked amount as `reported_gross`. A reader can see a zero or invalid source value and see that it did not contribute to the financial comparison. [Candidate reports](../src/streamvault/recommendation_reports.py)

Matching cleaned titles and release years flags possible duplicate films. Each flagged ID is retained and listed for review. Any window containing a flagged release gets provisional shortlists and any ratings preference is provisional. This errs on the side of review because keeping or dropping a duplicate could change eligibility or the comparison. A repeat of the same cache ID is a structural failure and stops the run.

Keep plausible IQR extremes in the primary analysis and use omission as a sensitivity case. Discarding observations because they are rare would remove some of the films most relevant to the bundle decision. Keeping a plausible outlier can make a result depend heavily on one title, so report influence and disclose when the direction changes. [EDA](../notebooks/03_eda_movie_data.ipynb)

Notebook 03 keeps numeric correlations and the unusual-value sensitivity comparison. The search for the best combination of fields to predict each numeric measure was removed. That search could suggest follow-up models, but the licensing decision uses observed audience ratings and reported gross. The focused table uses four pairs that inform metric choice. Each pair uses the same films for both measures and shows how the result changes when unusual values are left out. Category medians show a separate count for each measure and use only usable ratings, votes, and positive reported budgets and grosses. The tables compare film outcomes by genre, collection membership, collection, and talent, and preserve the number of observed films and talent groups. Per-film medians describe the films in each group. Using total gross would favor groups with more observed films. [EDA](../notebooks/03_eda_movie_data.ipynb)

### D04 · Keep the canonical types and measure runtime separately

Notebook 02's copy-only experiment cut the 112-film movie table by 10.6%. The first 500-title attempt exposed a problem with narrowing IDs. The talent analysis fills blank collection IDs with standalone movie IDs to build film groups. Even when every collection ID fits the smaller type, movie IDs can exceed it. The measured compact version kept both ID columns at their original sizes. It stored repeated release status and language labels once per label, and chose smaller integer types for budget, gross, runtime, and votes only when the values fit. [Profile](../notebooks/02_profile_movie_data.ipynb) · [Memory benchmark](../scripts/benchmark_movie_types.py)

| Measure | Original types | Compact types |
| --- | ---: | ---: |
| Normalized movie table | 571.7 KiB | 509.9 KiB |
| Peak analysis process memory | 395.7 MiB | 396.1 MiB |
| Cached analysis runtime | 3.57 s | 3.60 s |

The medians come from three fresh processes per version on the same 500 cached test records built from the 112-film snapshot. These measurements use the pipeline's shared cached analysis. The runtime covers loading saved inputs through writing reports and checking fingerprints. Acquisition and test-data setup sit outside the timer. Peak memory covers the analysis process including imports. Both versions produced identical join check results, shortlists, comparison results, and report contents. The conversion also preserved missing values and kept a wide type for a budget larger than the 32-bit limit. [Memory benchmark](../scripts/benchmark_movie_types.py)

**Decision.** Keep the original types in the pipeline. The smaller movie table saved 61.8 KiB (10.8%), mostly from storing repeated status and language labels more efficiently. The whole-run memory was effectively the same and runtimes overlapped, so the extra conversion has little practical benefit for Adjoa at this size. The separate scaling check took 1.54 seconds at 112 titles. The 500-title projection was 6.89 seconds and the measured run took 3.55 seconds. That projection assumes constant time per film, which can vary with the mix of titles and credits. [Timing script](../scripts/benchmark_recommendation.py)

### D06 · Rank by a fixed audience response measure

Notebook 03 now uses raw audience ratings for exploration. Using a second adjusted score would let results change with the candidate list and make similarly named figures hard to compare. Notebook 04 applies the fixed adjustment for the recommendation.

Give priority to the TMDB audience rating, shrunk toward 7.0 with weight equal to 1,000 votes. Use a minimum of 1,000 recorded votes for ranking. The fixed constants are analyst choices and apply identically across both windows and future reruns. The anchor sits below the current pool mean of about 7.59. At the threshold, audience votes and the anchor contribute equally. These choices can lower the rank of well-reviewed titles with fewer votes, which is why Notebook 04 tests the anchor and vote minimum separately. The EDA's cache-derived mean and vote quartile served exploratory comparisons.

Rank standalones by adjusted rating, votes, then numeric movie ID. Rank collections by median adjusted rating, lowest installment adjusted rating, median votes, then numeric collection ID. Order the performance metrics descending and IDs ascending. Use full precision and deterministic ties. Report vote count as evidence of breadth and popularity as snapshot context. A reach-first ranking could favor broader awareness and a gross-first ranking could favor larger or newer theatrical releases. Run reach-first, alternate eligibility thresholds and a lower rating anchor to show what each choice costs. A smaller candidate pool can produce fewer than the target three franchises or five standalones. [EDA](../notebooks/03_eda_movie_data.ipynb) · [Recommendation notebook](../notebooks/04_recommendation.ipynb)

The same package functions score and rank both windows and the scoring alternatives. The notebook fills all shortlist spots in this snapshot. It generates a report that gives each film a shortlist outcome for each window. For example, a film may have qualified and ranked below the cutoff. The report marks franchise ranks based on one film and lists source rows the pipeline could not use, including repeats. Each window shows eligible options and unfilled shortlist spots. A firm comparison is withheld if either side has fewer than five eligible options, even if one shortlist can still be filled. ### D07 · Compare equally weighted packages and single titles

TMDB collection membership supplies the hypothetical package. Allow one or more observed, dated, released films in the window and require usable rating evidence for each. The original two-film minimum excluded collections whose other installments fell outside the list or the release window. Removing it gives those collections a rank based on the available evidence. Label one-film scores so Kwame can see when the rest of the package still needs evidence. List the included installments and describe the gap between the list and the full package. A title without a collection ID is a standalone proxy. The lab comparison uses the observed list and its metadata.

Compare one median score per eligible collection with one score per standalone. Require at least five units per side and a descriptive 95% bootstrap interval beyond a 0.25 rating-point margin to favor either type. This margin is a judgment about how large a gap should be to drive a preference. Show the gap, the interval, and per-film comparisons so the reader can see how the rule affects the answer. Film weighting would give larger series extra influence. Summed gross grows with bundle size, so show it only alongside the typical film and remove the highest-scoring installment in a sensitivity run to expose reliance on the strongest entry. [Recommendation notebook](../notebooks/04_recommendation.ipynb)

The comparison applies the same rules to both windows. Sort numeric IDs and use seed 42 for 2,000 resamples within each group. The range uses the 2.5th and 97.5th percentiles of the gaps. For the omission check, remove the highest adjusted rating from each originally eligible bundle. Break film-score ties by lowest movie ID. Keep one-film bundles and drop empty bundles after removal. Save each omission so Adjoa can see which installments drove the change. Gross totals and per-film gross medians use positive reported gross even when budget is missing. Gross less budget uses films with both positive amounts. The ratings favor standalones in both windows before and after the omission. [Comparison code](../src/streamvault/recommendation.py)

### D08 · Base talent evidence on identities, roles and cross-group repetition

Notebook 03 now counts films and groups by ID and shows names as labels. Its earlier collection and talent rankings based on estimated gross gaps were removed. They added another ranking from incomplete collection and credit histories. Its genre model still tests whether adding tags improves held-out results, and related films can appear in different folds. Notebook 04 keeps related films together for its two-window genre test and checks how talent results change when the largest group is left out.

Use director crew jobs and cast orders 0–2 as the lead-cast proxy. Count distinct films by `person_id` and use IDs for collection membership. Require three films across two or more groups, with each collection or standalone representing one group. Assess directional sensitivity to leaving out the largest group. Keep the descriptive result when sample size or dependence limits the claim. A three-film-only rule can mistake one successful franchise for a transferable talent signal. Use period and collection-aware validation for any future predictive claim. [EDA](../notebooks/03_eda_movie_data.ipynb) · [Recommendation notebook](../notebooks/04_recommendation.ipynb)

The talent analysis reuses the fixed audience scores and the EDA genre thresholds. A median needs 10 films with the outcome. A model term needs 15 tagged films with the required inputs. Estimate gaps in rating points and log gross using log production budget, release year, collection membership, and common genres. Keep the same films and folds for the model comparison. The benchmark uses up to five folds that keep each collection together and a fixed Ridge penalty of 1 on standardized inputs to limit the effect of overlapping tags. Drop constant controls and fall back to controls alone when the training sets are too small for the genre terms. The benchmark compares films within each window and includes earlier and later releases in its training folds. The model outputs are descriptive. [Recommendation notebook](../notebooks/04_recommendation.ipynb)

Apply the three-film and two-group minimum to each benchmarked outcome. Remove the largest credited group from each person's median while keeping each remaining film's benchmark fixed. Break ties in favor of a collection, then the lowest numeric group ID. A comparison is fragile if fewer than two benchmarked films remain or the gap disappears or reverses. The screen keeps a hit franchise from driving the whole result and can still leave only a few films. Use a surviving signal as supporting evidence about this list.
